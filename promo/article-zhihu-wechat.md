# 我把 DeepSeek 的 Agent 工具装进了桌面,顺手开源了

## 一、那个不能关的终端窗口

第一次跑起 DeepSeek Harness 的那天晚上,我在屏幕上盯着两个窗口。

一个是终端,里面是 `dsh web` 的输出,几行日志,然后光标一直闪。另一个是 Chrome,地址栏 `127.0.0.1:3080`,一个干净的对话界面。我让它读了一遍我一个小项目的目录结构,它一边找文件一边解释自己在干什么,最后给了一份还算靠谱的重构建议。

那一刻我是兴奋的。DeepSeek 把自家的 agent harness 开源出来了,虽然还挂着 Dev Preview 的标签,但骨架已经在那儿:工具调用、文件读写、多轮任务。你不需要自己拼一个 agent loop,你只要有个 API key。

兴奋持续了大概三天。

第三天下午,我做了一件很蠢的事:整理任务栏,顺手关掉了那个「看起来没在干活」的终端。三十秒后浏览器标签页开始转圈。我这才反应过来——那个窗口不是没在干活,它就是 dsh 本身。

重开终端,`dsh web`,报错:端口 3080 已被占用。上一次的 node 进程还在后台活着,只是它的父进程 cmd 被我杀了,它变成了孤儿。`taskkill`,再起一次,回浏览器,刷新,标签页早已经被 Chrome 休眠掉了,重新加载,等,进去。

前后大概三分钟。为了一个我只想问一句话的问题。

那天晚上我打开编辑器,建了个文件夹叫 `dsh-client`。

![主界面](https://github.com/yace84295-ctrl/dsh-client/raw/main/docs/screenshots/screenshot-light.png)

## 二、浏览器不是不能用,是不合适

先说清楚:dsh 的 Web UI 做得没问题。问题在于**浏览器这个容器,和 agent 这类工具的使用节奏是错配的**。

我统计过自己的使用习惯:一天开十几次 dsh,每次平均停留一到三分钟。这是典型的「高频、短时长、随时打断」——和你用计算器、用剪贴板工具、用截图工具的节奏一样,而不是和你用 Photoshop 的节奏一样。

对这种节奏,浏览器有三个结构性的不适合:

**第一,它没有位置。** 浏览器里的一切都是标签页,平权地挤在一排。你的 agent 和你的知乎、文档、购物车是同一个层级的东西。而我需要的是一个「呼之即来」的东西,它得有自己的位置、自己的快捷键、自己的窗口尺寸记忆。

**第二,它不管进程。** 关掉浏览器不会 kill dsh,关掉终端会但会留孤儿。这个生命周期本来就该由一个东西统一管,而浏览器天生管不了。

**第三,它的状态不可靠。** 标签页会被休眠,会被误关,会在你重启浏览器后变成一个空的恢复提示。而 agent 会话是有上下文的,上下文被打断的代价比一个网页被打断的代价高得多。

结论就一句话:**agent 工具需要的是「工具位」,不是「标签页」。**

## 三、为什么是 Electron,为什么是这几个设计

有人会说,Electron?92 MB 装一个 iframe?

是的,我完全知道这个选择的批评在哪。但我需要的东西列出来之后,答案很自然:

- 我要**复用 dsh 现成的 Web UI**——上游在快速迭代,我不想跟着重写前端;
- 我要**管子进程**——需要 `child_process`、`taskkill`、HTTP 轮询;
- 我要**全局快捷键**——窗口隐藏时也能唤起;
- 我要**一个文件就能跑**——用户不该为了用它先装 Node.js;
- 我要**两小时能写完**。

Electron 全都给我了,而且是唯一一个全都给我的。技术栈最终是 Electron 32 + Node.js 24,splash 的动效用了点 Three.js。

至于 92 MB:这里面装的是完整的 Chromium + Node 运行时,换来的是**终端用户零依赖**。他下载一个 portable exe,双击,完事。不装 Node、不配环境变量、不要管理员权限。我认为这个交易划算。

几个具体的设计决定:

**自定义标题栏(无边框 + 玻璃效果)。** 不是为了好看,是因为我要在标题栏上放高频入口:命令面板、日志、路径设置。系统标题栏那块空间在这类工具里是浪费的。

**全局快捷键优先于界面按钮。** 我给自己定的标准是:最高频的三个动作(唤起、重启 dsh、切主题)必须一次按键完成,不许经过任何界面。所有 8 个全局快捷键在 `src/shortcuts.js` 里是一份纯数据表,加一条就是加一个对象。

**先开启动画面,再开主窗口。** 因为 dsh 冷启动要几秒,如果那几秒里屏幕上什么都没有,用户第一反应是「双击没反应」,第二反应是再双击一次。splash 上有进度条、有阶段提示(初始化 → 启动 dsh → 等待端口 → 就绪),失败时直接显示具体原因。

## 四、五个我自己每天在用的功能

### 1. `Ctrl+Shift+D`:呼之即来

窗口隐藏在托盘里,一次按键出现,出现在你上次放它的位置和大小,再按一次收回去。

这是整个项目最有价值的功能,也是最不起眼的功能。它把「我想问 dsh 一句话」的成本从三十秒降到半秒——而成本降到某个阈值以下之后,你使用它的频率会跳一个台阶。我现在会为很小的事情用它:「这个正则啥意思」、「这行报错大概是啥」。之前这些问题我会自己硬看,因为「开一下 dsh 太麻烦了」。

### 2. `Ctrl+Shift+R`:dsh 抽风了就重启它

dsh 还是 Dev Preview,偶尔会卡住不响应。以前的流程是:找终端 → `Ctrl+C` → 重新 `dsh web` → 回浏览器 → 刷新。现在是一次按键:kill 子进程 → 重新 spawn → 轮询端口 → 刷新 UI,全自动。

关掉 app 时也会自动清理:`taskkill /f /t` 整个进程树。再也没有过孤儿 node 占端口的事。

### 3. `Ctrl+K`:命令面板

13 条命令,VS Code 那套交互:模糊搜索、上下键选、回车执行。切主题、截图、重启 dsh、刷新 UI、浏览器打开、设置 dsh 路径、查看日志、关于、退出……全在里面。

我最常用的是「在系统浏览器中打开 dsh」——有时候我确实需要把某个长回答丢到浏览器里慢慢看,或者用浏览器的翻译。桌面客户端不应该把你锁死在自己里面。

![命令面板](https://github.com/yace84295-ctrl/dsh-client/raw/main/docs/screenshots/command-palette.png)

### 4. `Ctrl+Shift+L`:日志查看器

1000 行环形缓冲,把 dsh-client 自己的日志和 dsh 子进程的 stdout/stderr 全收进来,支持搜索、复制、清空。

这个功能是在调试中长出来的,但它对普通使用者更有意义:当 dsh 不响应的时候,你能立刻看到它到底在等什么——是 API 超时,是 key 没读到,还是它自己崩了。**在一个还在 Dev Preview 的工具上,「可观测」不是奢侈品。**

### 5. `Ctrl+Shift+T`:深色 / 浅色主题

一键切,持久化,标题栏跟着变。白天浅色,晚上深色。听起来是最没技术含量的功能,但它是我按得第二多的键。

![深色主题](https://github.com/yace84295-ctrl/dsh-client/raw/main/docs/screenshots/screenshot-dark.png)

另外还有一些不需要你操心的东西:自定义 dsh 路径(找不到时弹原生对话框让你选,存下来)、窗口位置记忆(多显示器场景会校验 bounds 是否落在真实存在的屏幕上,拔了外接屏也不会窗口消失)、单实例锁(二次启动聚焦已有窗口而不是开第二个)。

## 五、从「能跑」到「能开源」,后面那一半的工作

代码本身两小时就通了。但从「我自己能跑」到「能挂在 GitHub 上给人用」,又花了差不多同样的时间。这部分我觉得值得单独说,因为很多人卡在这里。

**模块化不是洁癖,是为了能测。** `src/` 下拆成 8 个模块,判断标准很朴素:**能不 import electron 就不 import**。像进程管理这种最容易出 bug 的核心逻辑,拆出来之后可以在纯 Node 环境里跑单测,不用起整个 Electron。最后是 124 个 Vitest、76.5% 覆盖率。剩下那 23.5% 基本是必须真跑窗口的代码,那部分我手测。

**README 要写给三种人。** 想直接用的(下载 exe,三步走完)、想改代码的(clone、npm install、npm start)、想知道这是啥的(功能列表 + 截图)。中英双语,因为 dsh 的用户显然不只在中文区。

**故障排查章节的价值被严重低估。** 我把自己踩过的坑全写进去了:端口被占了怎么办、API key 没读到查哪个文件、`npm install` 拉 Electron 卡住要设 `ELECTRON_MIRROR`。这几行字能省掉的 issue 数量,比任何代码优化都多。

**CI 四条流水线:** `test.yml`(测试 + lint)、`lint.yml`(风格)、`build.yml`(打 .exe)、`release.yml`(发布)。开源项目里 CI 的真正作用不是「保证质量」,是**让陌生人的 PR 有一个客观裁判**——不然你只能凭感觉说「我觉得这样不太好」,那种对话很消耗人。

**该有的文件都得有:** LICENSE(MIT)、CHANGELOG、CONTRIBUTING、SECURITY、CODE_OF_CONDUCT。这五个文件加起来写不了多久,但它们是在告诉来访的人:这个仓库有人在管,你的 PR 不会被无视,你发现漏洞知道该发给谁。

## 六、AI Agent 工具的「桌面化」,可能才刚开始

写完这个东西之后,我一直在想一件事。

过去两年 AI 工具几乎清一色是 Web 优先:开个网页、贴个 key、开始聊。这个路径在「对话」这个形态下是完美的——无摩擦、跨平台、随时可以推新版本。

但 agent 不是对话。agent 是**长时间运行、要访问本地文件、要管理子进程、会在后台干活、需要你随时打断和查看**的东西。这几个特征拼在一起,恰好是浏览器沙箱最不擅长的地方。

于是我们看到一个明显的转向:Claude 出了桌面端和 Code CLI,OpenAI 出了 Codex,一堆 agent 框架都在往本地跑。它们不是在跟浏览器赌气,而是因为 agent 的能力上限被容器卡住了——你没法在标签页里安全地读用户的文件系统,你没法在标签页里保证一个跑了半小时的任务不被休眠。

我的判断是,接下来一两年,agent 工具的形态会更像**系统级常驻工具**,而不是网站:有托盘图标、有全局快捷键、有本地配置、能管自己的子进程、退出时自己清理干净。它更接近 Everything、更接近 Raycast、更接近输入法,而不是更接近一个网页。

`dsh-client` 严格来说只是个壳,它没有给 dsh 增加任何 AI 能力。但它给 dsh 补上了「作为一个本地工具」该有的那部分:位置、快捷键、生命周期、可观测性。而我觉得这部分恰恰是当下大量 agent 项目缺的——**模型能力已经够用了,把它放进一个顺手的容器里,收益往往比再调一轮 prompt 大。**

如果你在做 agent 相关的东西,不妨想想你的用户是在什么节奏下使用它。如果答案是「一天十几次、每次一分钟」,那你可能也需要一个桌面壳。这个仓库是 MIT 的,进程管理、全局快捷键、命令面板、日志缓冲那几块可以直接抄走,不用客气。

## 七、来试试

- **仓库**:https://github.com/yace84295-ctrl/dsh-client
- **下载**:Releases 页面,`dsh-client-portable-0.3.1.exe`,92 MB,免安装,不要管理员权限
- **前置**:Windows 10/11、dsh(`npm i -g deepseek-harness`)、一个 DeepSeek API key
- **License**:MIT

第一次启动如果找不到 dsh,它会弹窗让你手动指路径,选一次就记住了。

想插手的话,`CONTRIBUTING.md` 里有环境搭建步骤。Roadmap 上现在挂着:真正的 auto-update(现在是 stub)、macOS/Linux 构建(进程树清理那块得重写)、端口可配置以支持多实例、系统级全局唤起。这几个我短期都不一定动得了,谁想拿走都行。

如果你也在用 dsh,也受不了那个不能关的终端窗口,希望这个东西能帮你省下那三分钟。
